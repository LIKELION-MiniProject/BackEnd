## 2) reasons 배열 순서 (명문화)

**recommendation.reasons 는 정확히 3개이며 순서가 고정된다: `[0]=성향 맞춤(규칙), [1]=과목 특성(AI), [2]=졸업·전공 기여(AI)]`. FE 는 인덱스 위치로 라벨(나에게 맞음 / 과목 특성 / 졸업·전공 도움)을 렌더한다.** 폴백 시에도 같은 순서로 3개(모두 규칙 생성).

## 3) caution 규칙 (명문화)

- `caution`은 **EXAM_SOLO·TEAM_ACTIVE** 두 방향에만 값이 있고, 나머지는 `null`.
- **thin 방향(`thin=true`)에는 caution 을 넣지 않는다**(`null`). 편향 안내와 thin 안내가 겹치지 않도록. thin 안내는 FE thin 박스가 담당.
  - 예: TEAM_ACTIVE 가 매칭 2개라 thin 이면 → `caution=null`, `thin=true`.
  - EXAM_SOLO 가 매칭 5개(비-thin)면 → `caution="시험 비중이 높아 시험 부담이 클 수 있어요."`.
- FE: `caution!=null` 이면 라벨 아래 **빨간 글씨**. 문구는 서버가 준다(FE 하드코딩 금지).

## 4) thin 정책 (명문화)

- 매칭 **0개** 방향 → `directions` 배열에서 **제외**(빈 탭 방지).
- 매칭 **1~4개** 방향 → 배열에 포함, `thin=true`, **그 개수 그대로**(5개로 패딩하지 않음).
- 방향 내부에서만 보충(그 방향 매칭 후보). **다른 방향/후보 밖 과목으로 5개를 채우지 않는다** → UI thin 박스의 "N개만 안내"와 일치.

## 5) directionId ↔ name 확정 라벨 (26 문서 표기 = 확정본)

| directionId | name(확정) | caution |
|---|---|---|
| `FAST_GRAD` | 졸업요건 집중형 | null |
| `MAJOR_DEEP` | 전공 심화형 | null |
| `GRADE_SAFE` | 학점 안정형 | null |
| `EXAM_SOLO` | 시험·개별평가형 | (비-thin일 때) "시험 비중이 높아 시험 부담이 클 수 있어요." |
| `TEAM_ACTIVE` | 협업·활동형 | (비-thin일 때) "팀플·발표 비중이 높아요. 협업 경험을 넓히려는 분께 권하는 선택적 도전이에요." |

> `directionId`는 코드 고정값(변경 금지). 신영 PNG 라벨이 다르면 표시명만 맞추고 directionId 유지.

## 6) source & 배지 규칙 (명문화)

- `source` ∈ `live | cache | fallback`.
- **cache 는 화면상 live 와 동일 취급**(정상 추천). 초록 "AI 분석 완료" 배지.
- **"기본 추천" 배지는 `source=="fallback"` 일 때만** 표시(앰버). AI 실패 → 규칙 추천 상황.

## 7) 데모 응답 구조 (예시 3종의 공통 형태 — MAJOR_DEEP 없는 케이스)

```
directions: [
  FAST_GRAD    (n=5, thin=false, caution=null),
  GRADE_SAFE   (n=1, thin=true,  caution=null),
  EXAM_SOLO    (n=5, thin=false, caution="시험 비중이 높아…"),
  TEAM_ACTIVE  (n=2, thin=true,  caution=null)   // thin 이라 caution 억제됨
]
defaultDirectionId: "FAST_GRAD"
recommendations(최상위) = FAST_GRAD 5개 미러
```
- MAJOR_DEEP 은 전공 후보 0 → 배열에서 제외(정상). 5방향이 다 차는 화면은 전공 부족 2번째 데모 계정으로 시연.

## 8) 팀 공유 문구

### 인서(FE)에게
> "AI 추천 계약 v2.1 확정본 공유해. 변경/확정점 4가지.
> ① reasons는 항상 3개, **순서 고정 [성향맞춤 / 과목특성 / 졸업·전공기여]** — 위치로 라벨 렌더하면 돼.
> ② 각 방향에 `caution`(null이면 미표시, 문자열이면 빨간 글씨) + `thin`(true면 얇게, 매칭 개수 그대로). **thin이면 caution은 안 와**(null) — 그 방향은 thin 박스로만 안내.
> ③ `source`가 cache면 live랑 똑같이 정상 화면. **'기본 추천' 배지는 fallback일 때만.**
> ④ 각 과목에 `category`(전공필수/전공선택/교양 등) — 있으면 '구분 · N학점', 없으면 'N학점'.
> 실데이터 목업 3종(live/cache/fallback, 데모 학생처럼 MAJOR_DEEP 없는 케이스) 첨부했어. `src/mocks/`에 넣고 붙이면 돼.
> 그리고 상단 **스탯 카드 3종(성적 분석·졸업요건 충족률·선수과목 확인)은 추천 응답 밖 데이터**야. 지금 화면에서 그 값이 진단/GPA/대시보드 API에서 오는지, 아니면 데모 하드코딩인지 확인해서 알려줘(원석 보고용)."

### 신영(디자인)에게
> "방향 탭 라벨 확정: 졸업요건 집중형 / 전공 심화형 / 학점 안정형 / 시험·개별평가형 / 협업·활동형.
> caution(빨간 경고)은 시험·개별평가형·협업·활동형에만, 그것도 과목이 충분할 때만 떠(적으면 thin 안내로 대체). 이유 칩은 항상 3개 고정순서(성향맞춤/과목특성/졸업·전공기여)."

## 9) ⚠️ 원석 보고 대기 (스탯 카드 출처)

UI 상단 스탯 카드 3종(성적 분석 %, 졸업요건 충족률 %, 선수과목 확인)은 **RECO 응답 밖 데이터**다. 현재 FE가 이 값을 어디서 받는지(진단 API `GET /diagnosis` / GPA `GET /gpa-trend` / 대시보드 `GET /dashboard` vs 데모 하드코딩) **인서 확인 후 보고**만 한다. 추천 API에 넣지 않는다.

## 1. 🔴 `batch.py` 절차가 실행 불가능했다

### 문서에 적혀 있던 것 (82 §3, 85 §2 초판)

```bash
python batch.py 2024132075     # 실데이터 캐시 생성
```

### 실제 코드

```python
# batch.py
def main():
    cmd = sys.argv[1] if len(sys.argv) > 1 else "demo"
    {"demo": cmd_demo, "candidates": cmd_candidates, "models": cmd_models}.get(cmd, cmd_demo)()
```

- 받는 인자는 **`demo` / `candidates` / `models` 3개뿐**
- `.get(cmd, cmd_demo)` — **모르는 인자는 전부 `cmd_demo()`로 조용히 폴백**
- `cmd_demo()`는 `from_demo()`로 `data/demo_*.json`을 읽는다 → studentKey는 **항상 `202312345`**

### 왜 아무도 몰랐나 (핵심)

2단계에서 실행한 `python batch.py 202312345`가 **성공한 것처럼 보였다.** 인자가 무시되고 demo가 돌았는데, **demo 데이터의 studentKey가 우연히 `202312345`라서 결과가 맞아떨어졌다.**

> 즉 **"실데이터로 돌렸다"고 믿고 있었지만 실제로는 데모가 돈 것**이다. 학번이 우연히 일치하지 않았다면 즉시 드러났을 문제다.

만약 이대로 5단계에서 `python batch.py 2024132075`를 실행했다면:
- 원석 캐시는 **생성되지 않고**
- **데모 캐시(`202312345.json`)가 조용히 덮어써졌을 것** (사고 #4의 재발)

### 어떻게 발견했나

85 문서의 절차를 실행하기 전에 `batch.py` 코드를 읽었다. 게이트 당일이라 "실행 전 확인"을 한 것이 사고를 막았다.

### 진짜 경로

`bridge.py` 헤더에 명시돼 있었다:
> *"캐시: recommend()가 결과를 cache/{studentKey}.json에 항상 저장한다."*

```
POST /api/v1/profiles/{id}/recommendations
  → RecommendationService.generate()
  → PassportAiBridge → bridge.py (stdin: payload JSON)
  → core/recommend.recommend()
  → core/cache.write_cache(studentKey, result)   ← cache/{studentKey}.json 생성
```

**결론 : 임의 학번의 캐시는 `POST /recommendations` 1회로만 만들 수 있다. `batch.py`는 데모 전용이다.**

### 조치

- 83·85 문서 정정, [86 §1](86_캐시_persona_메커니즘_실측기록.md)에 상세 기록
- 원석 캐시는 `POST`로 생성 완료 → 5방향 확인
- **백로그** : `batch.py`에 `argparse` 도입 — 모르는 인자는 **조용히 폴백하지 말고 에러**를 내야 한다. 이 "조용한 폴백"이 문제의 근본 원인이다.

## 2. 🔴 h2-console이 인터넷에 노출될 뻔했다

### 발견 경위

AWS 배포(블록 D) 중 systemd 유닛에 `SPRING_PROFILES_ACTIVE=prod`를 넣기 직전, **`application-prod.yml`이 실제로 있는지** 확인하다 발견.

### 문제 3중 결합

1. **`application-prod.yml`이 존재하지 않는다** → `SPRING_PROFILES_ACTIVE=prod`는 **아무 효과 없음**
2. `application.yml`에 `spring.h2.console.enabled: true`
3. `SecurityConfig:45` → **`.requestMatchers("/h2-console/**").permitAll()`**

여기에 보안그룹 **`8080` = `0.0.0.0/0`** 이 겹치면 → **인터넷 누구나 H2 DB 콘솔에 접근 가능.**

> 로컬 개발에서는 문제가 안 되던 설정이, **외부 공개 서버로 나가는 순간 보안 구멍**이 됐다. `prod` 프로파일이 있을 거라는 암묵적 가정이 깨진 것이 원인이다.

### 조치 — 코드 수정 없이 차단

기능 동결을 지키기 위해 Spring relaxed binding을 이용한 **환경변수 override**:

```ini
Environment="SPRING_H2_CONSOLE_ENABLED=false"   # = spring.h2.console.enabled
```

콘솔 서블릿 자체가 등록되지 않으므로 `permitAll`이 무의미해진다. **브라우저 접근 차단 확인 완료.**

### 남은 것

- 404가 아니라 `{"code":"COMMON-004"}`(500)가 반환된다 — 전역 예외 핸들러가 미매핑 경로를 잡아서. **콘솔 미노출이라는 목적은 달성**했으므로 게이트 범위에선 문제없음
- **백로그** : `application-prod.yml` 신설 + `SecurityConfig`의 `/h2-console/**` permitAll을 **dev 프로파일 전용**으로 분리

## 3. 🔴 전공 과목 평가특성이 전부 비어 있었다

### 증상

원석 실데이터로 `POST /recommendations` 했더니 **추천 방향이 2개만** 나왔다(`FAST_GRAD`, `MAJOR_DEEP`). 공유 ① 시연 대본은 **"5방향 탭"**이었다.

### 원인

`core/directions.py`:

```python
def classify(candidates, facts):
    for spec in SPECS:              # [FAST_GRAD, MAJOR_DEEP, GRADE_SAFE, EXAM_SOLO, TEAM_ACTIVE]
        matched = _filter(spec, candidates, facts)
        if not matched:             # ← 빈 방향은 아예 노출하지 않음
            continue
```

| 방향 | 필터 조건 | 특성 의존 |
|---|---|---|
| `FAST_GRAD` | 미이수 영역 우선 + 학점 순 | ❌ 무관 |
| `MAJOR_DEEP` | `category == MAJOR` | ❌ 무관 |
| `GRADE_SAFE` | `gradingStyle == "너그러움"` and 시험≠많음 and 팀플≠많음 | ✅ 필요 |
| `EXAM_SOLO` | 시험∈(많음,보통) and 팀플∈(없음,None) | ✅ 필요 |
| `TEAM_ACTIVE` | 팀플∈(보통,많음) or 발표∈(보통,많음) | ✅ 필요 |

그리고 `courses_eval.csv` 실측:

| 구분 | 전체 | 특성 보유 |
|---|---|---|
| 교양선택 | 140 | 135 |
| 교양필수 | 11 | 5 |
| **전공** | **31** | **0** 🔴 |

**전공 특성이 전부 공란**이라, 부족영역이 전공인 학생(=원석)은 후보가 전부 전공 → 특성 의존 3방향이 0개 매칭 → 제외 → **2방향만 노출**.

> demo(`202312345`)가 4방향이었던 건 부족영역이 교양(`[4,6]`)이라 후보가 교양(특성 보유)이었기 때문. **데이터 특성에 따라 방향 수가 달라진다** — 데모만 보고 있으면 절대 안 드러나는 문제였다.

### 조치

원석이 실제 수강 경험 기반으로 작성한 Notion 표 + 구술 설명을 `courses_eval.csv`에 **11과목 반영** → `build_data.py` 재실행 → EC2 업로드 → 캐시 재생성.

> **기능 동결과 무관** — 코드가 아니라 **데이터** 보강이다.

**결과 : 2방향 → 5방향** ✅

| 방향 | 과목 | thin | caution |
|---|---|---|---|
| 졸업요건 집중형 | 5 | — | — |
| 전공 심화형 | 5 | — | — |
| 학점 안정형 | 1 | **thin** | — |
| 시험·개별평가형 | 5 | — | **"시험 비중이 높아 시험 부담이 클 수 있어요."** |
| 협업·활동형 | 3 | **thin** | — |

부수 효과로 **thin 배지와 caution 문구를 실물로 시연**할 수 있게 됐다(신영님 톤 점검 대상).

### 남은 것

- **전공 20과목은 여전히 공란** (31 중 11만 보강)
- **9과목의 `성적후함정도` 미확보** → `GRADE_SAFE`가 thin(1과목). 7/16 확보 시 해소

## 4. 🟠 추천 캐시 덮어쓰기 사고

### 무슨 일이 있었나

82 §3 검증 시나리오 8번(`POST /recommendations`)을 실행했더니, **`source: "live"`로 Gemini를 실호출하면서 `passport-ai/cache/202312345.json`(git 추적 파일)을 덮어썼다.** (118줄 추가 / 154줄 삭제)

### 왜 나빴나

덮어쓴 시점의 데이터는 **테스트 과목 1개("데이터베이스", 카탈로그에 없는 이름)만 있던 상태**였다. 그래서 새 캐시의 persona가 **`EXPLORING`(탐색형)** — *"아직 성향을 분석할 만큼의 성적 데이터가 충분하지 않아요"* 로 박제됐다.

이대로 뒀으면 **발표 데모에서 잘못된 "탐색형"이 노출**됐을 것이다.

### 근본 원인

- `POST /recommendations`가 **검증 명령이면서 동시에 상태 변경 명령**이다. "확인만 해보자"가 곧 "덮어쓰기"였다
- 81 문서는 캐시 재생성을 **STEP 3의 별도 작업**으로 명시했는데, 검증이 그 경계를 모르고 침범했다

### 조치

- git 추적 확인 → `git checkout -- passport-ai/cache/202312345.json`로 복원
- 2단계에서 정상 데이터로 재생성 (persona `INDIV_STRONG`, directions 4개)
- **운영 규칙 확정** :
  | # | 규칙 |
  |---|---|
  | ① | 최종 캐시 생성 후 **`batch.py demo` 재실행 금지.** 서빙 검증은 **Spring GET으로만** |
  | ② | live 검증이 필요하면 **캐시 백업 후** 실행. 폴백 검증은 **`.env` 임시 리네임** |

## 5. 🟠 지문(fingerprint)에 카탈로그가 포함되지 않는다

### 증상

전공 특성 11과목을 보강하고 EC2에 올린 뒤 `POST /recommendations` 했는데 — **`generatedAt`이 이전 값 그대로**였다. 재생성이 안 된 것이다.

### 원인

`RecommendationService.generate()`:

```java
String currentFp = fingerprint(profile);                  // 유저 입력 데이터의 지문
Optional<String> storedFp = readFingerprint(studentId);   // cache/{studentId}.fp

if (cached.isPresent() && storedFp.isEmpty()) {
    writeFingerprint(studentId, currentFp);
    return withFreshPersona(cached.get(), profileId);     // ① 캐시 유지 + 지문만 기록
}
if (cached.isPresent() && currentFp.equals(storedFp.get())) {
    return withFreshPersona(cached.get(), profileId);     // ② 변화 없음 → 캐시 유지
}
// ③ 데이터 변경/첫 생성 → 라이브 재생성
```

| 지문에 | 항목 |
|---|---|
| ✅ 포함 | **유저 입력 데이터** — 수강 이력 · 요건 · 인증 · 프로필 |
| ❌ **미포함** | **카탈로그(`data/courses.json`)** — 과목 특성 · 학점 · 영역 |

**카탈로그를 아무리 고쳐도 지문이 그대로라 캐시가 영원히 재생성되지 않는다.**

### 함정 — `.fp`만 지우면 안 된다

`.fp`만 삭제하면 위 분기 **①**(`cached.isPresent() && storedFp.isEmpty()`)에 걸려서 **캐시 유지 + 지문만 기록**되고 재생성되지 않는다. 이 분기는 "지문 도입 이전에 만들어진 데모 캐시를 보호"하려는 의도인데, 강제 재생성을 시도하면 오히려 방해가 된다.

### 조치 (우회)

```bash
# 반드시 .json 과 .fp 를 함께 삭제
rm -f ~/app/passport-ai/cache/{학번}.json ~/app/passport-ai/cache/{학번}.fp
# → POST /recommendations 1회
```

- 원석 캐시(`2024132075`)만 삭제 — 데모 캐시(`202312345`)는 보존 확인
- **백로그** : 지문에 카탈로그 버전(해시/mtime)을 포함시켜야 데이터 갱신이 반영된다

### 알아둘 부수 효과

- **수강 과목을 추가·삭제하면 지문이 바뀌어 다음 POST에서 자동 재생성**된다 → 시연 시나리오 "과목 라이브 추가"를 하면 AI가 재호출되고 캐시가 갱신된다. 의도된 동작이나 **리허설에서 추가한 과목은 그대로 남는다**
- `source`가 `live`일 때만 지문을 저장 → AI 일시 실패(폴백) 시 다음 클릭에서 자동 재시도

## 6. 🟠 persona 산출 조건이 문서와 달랐다

### 문서에 쓰여 있던 것

83 초판: *"특성 보유 과목은 **주로 교양**"*

### 실제

**전공 31과목 중 특성 보유 0건.** "주로 교양"이 아니라 **100% 교양**이었다. 표현의 문제가 아니라 판단이 갈리는 차이다 — 전공 위주로 입력하면 persona가 **반드시** 탐색형이 된다.

### 82 문서 예시 과목의 문제

82 §3-2 검증 시나리오가 예시로 쓴 **`"데이터베이스"`는 카탈로그에 아예 없는 과목**이었다. 그래서 검증 중 `pattern=none 코드매핑=0과목 미매칭=1과목`이 나왔고, 이것이 "persona가 고장났나?"라는 오해를 잠시 유발했다.

### 실측으로 확정한 조건

```
persona 브릿지 성공: pattern=none     코드매핑=0과목
persona 브릿지 성공: pattern=none     코드매핑=1과목
persona 브릿지 성공: pattern=none     코드매핑=2과목
persona 브릿지 성공: pattern=balanced 코드매핑=3과목   ← 전환
```

**두 조건을 모두 충족해야 패턴이 나온다:**
1. **과목명이 `data/courses.json`과 정확 일치** (`bridge.py`가 공백 트림 후 exact match)
2. **매핑된 과목에 평가특성이 있어야** 함 — **3과목 이상**에서 `balanced` 전환 확인

### 결과 — 리스크는 해소됐다

원석 실데이터에 **특성 보유 교양이 7과목** 있어 임계값을 넘겼다 → **persona `균형 성장형(BALANCED)` 산출.** 시연용 과목을 억지로 넣을 필요가 없었다.

단 **과목명을 카탈로그 정확명으로** 넣어야 했다:

| 시간표 표기 | 카탈로그 정확명 |
|---|---|
| 데이터분석의기초 | **데이터분석의기초(MD)** |
| 창의적사고와코딩 | **창의적사고와코딩(MD)** |
| 인성과대학생활 | **인성과대학생활Ⅰ** |
| 인성과미래설계 | **인성과미래설계Ⅰ** |
| 인공지능플랫폼설계 | **인공지능 플랫폼 설계** (띄어쓰기) |

카탈로그에 없는 `인공지능캡스톤`·`영어읽기와쓰기`는 **미매칭으로 조용히 제외**된다(에러 아님). 학점 계산은 Spring 진단이 이미 끝낸 값을 쓰므로 **진단에는 영향 없음**.

## 7. 🟠 내 분석 실수 — 잘못된 보고를 했다

투명하게 기록한다. **한 번 틀린 결과를 원석에게 보고했다.**

### 무슨 일

과목-카탈로그 대조 스크립트에서 `데이터분석기초`를 **"❌ 카탈로그 없음"**으로 보고했다. **틀린 결과였다** — 실제로는 `401354`로 존재한다.

### 원인 (2중 실수)

1. **CSV 헤더가 따옴표로 2줄에 걸쳐 있어** `csv.reader`가 이를 **1행으로 합친다.** 나는 `rows[2:]`로 잘랐고, 그 결과 **첫 데이터 행(`데이터분석기초`)을 날렸다**
2. **기준 파일을 잘못 골랐다** — `bridge.py`가 실제로 매핑에 쓰는 건 `courses_eval.csv`가 아니라 **`data/courses.json`**이다

### 어떻게 알아챘나

앞선 검증에서 `데이터분석기초`를 등록했을 때 로그에 **`코드매핑=1과목`**이 찍혔던 것과 **모순**됐다. 이전 실측 결과와 안 맞아서 재확인했다.

### 조치

- `courses.json` 기준으로 재대조 → 정확한 결과 확보
- `awk`(182행)와 `csv.reader`(181행)의 **행 수 불일치**가 이 버그의 신호였다. 이후 분석에선 두 방식의 결과를 교차 확인

### 교훈

- **파싱 결과가 이전 실측과 모순되면 파싱을 의심할 것.** 실측 로그가 정답이다
- **런타임이 실제로 읽는 파일**을 기준으로 삼을 것. 원본(raw)과 빌드 산출물이 다르면 산출물이 진실이다

## 8. 🟡 `Course.credit`이 `int`라 0.5학점을 못 담는다

- `인성과미래설계Ⅰ` — 성적표 **0.5학점**, 카탈로그 **0학점**, 등급 `P`
- `Course.credit`이 `int`라 저장 불가. `0.5`를 보내면 400 에러
- 유지하려면 엔티티·DTO·진단 계산을 `double`로 바꿔야 하는데 **게이트 4시간 전 기능 동결 위반**
- **조치** : 원석 결정으로 **`credit=0`** (카탈로그 등록값과 일치). `P`라 GPA 무관, 130학점 요건 대비 0.5 차이라 진단 영향 미미
- **결과** : 총 이수 39학점 (성적표 기준 39.5)

## 9. 🟡 PowerShell 5.1 UTF-8 디코딩 버그 — 검증을 오판할 뻔했다

### 증상

`Invoke-RestMethod`로 로그인했더니 nickname이 **`ë°ëª¨ì ì 1`**로 깨져 나왔다.

### 왜 위험했나

이 세션의 검증 항목 중 하나가 **"한글 라벨(`재학생`/`해당 없음`)이 제대로 나오는가"**였다. 도구가 한글을 깨뜨리면 **정상 동작을 실패로 오판**하거나, 반대로 실제 인코딩 문제를 도구 탓으로 넘길 수 있었다.

### 원인

Windows PowerShell 5.1은 `Content-Type: application/json; charset=UTF-8`을 무시하고 JSON 응답을 시스템 코드페이지로 디코딩한다(알려진 버그).

### 조치 — RawContentStream 수동 디코딩

```powershell
function J($m,$u,$h,$b){
  $p=@{Method=$m;Uri=$u;Headers=$h;UseBasicParsing=$true}
  if($b){$p.ContentType="application/json";$p.Body=[Text.Encoding]::UTF8.GetBytes($b)}
  $r=Invoke-WebRequest @p
  return [Text.Encoding]::UTF8.GetString($r.RawContentStream.ToArray())   # ← 핵심
}
```

이후 `데모유저1`, `재학생`, `해당 없음` 정상 확인.

### 파생 사례

- `Get-Content`도 동일 — **`-Encoding UTF8`** 없이 `.env`를 읽으니 한글 주석이 깨져 **`GEMINI_API_KEY`가 없는 것처럼 보였다**(실제로는 주석 줄에 섞여 잘린 것). 필터를 걸어 재확인 후 항목 2개 확정
- **서버 응답 자체는 처음부터 정상**이었다. 전부 클라이언트 표시 문제

## 10. 🟡 `$pid`는 PowerShell 예약 변수다

```powershell
$pid = ($pr | ConvertFrom-Json).data.id
# → Cannot overwrite variable PID because it is read-only or constant.
```

- `$pid`는 현재 프로세스 ID를 담은 **read-only 자동 변수**
- 대입이 실패했는데 **스크립트가 멈추지 않고 계속 실행**됐다 → `$pid`에 프로세스 ID(`37092`)가 들어간 채로 `PATCH /profiles/37092` 호출 → `404 PROFILE-001`
- **다행히 404로 끝났지만, 만약 그 ID의 리소스가 존재했다면 엉뚱한 프로필을 덮어썼을 것이다**
- **조치** : `$myProfileId`로 변경. 이후 `auth/me`로 profileId를 조회해 사용

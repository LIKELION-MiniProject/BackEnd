# 데이터 저장 이원화 설계 리포트 — 왜 유저 데이터는 DB, 과목 카탈로그는 파일인가

> **작성일** : 2026-07-17
> **한 줄 요약** : 성격이 다른 두 데이터를 각자에게 맞는 저장소에 뒀다. **바뀌는 데이터(유저)는 DB**, **바뀌지 않는 데이터(카탈로그)는 파일**. 우연이 아니라 의도된 분리다.

---

## 1. 지금 구조

| 구분 | 저장소 | 내용 | 읽는 주체 |
|---|---|---|---|
| **H2 DB** | Spring (JPA) | 회원 · 프로필 · 수강이력 · 인증 · 요건 입력 | Spring (Java) |
| **`courses.json`** | 파일 (EC2 디스크) | 과목 카탈로그 182건 + 평가특성 | Python (`loader.py` · `bridge.py` · `persona.py`) |

두 저장소는 **역할이 겹치지 않는다.** DB는 "이 학생이 무엇을 했나", 파일은 "이 학교에 어떤 과목이 있나"를 담는다.

---

## 2. 두 데이터는 성격이 정반대다

| 성격 | 유저 데이터 (DB) | 과목 카탈로그 (파일) |
|---|---|---|
| 변경 주기 | **매 요청마다** (가입·입력·수정·삭제) | **거의 없음** (학기 단위, 정적) |
| 변경 주체 | 서비스 사용자 (런타임) | 개발팀 (빌드 타임) |
| 소유 단위 | 사용자별 (계정마다 다름) | 전역 공유 (모두 동일) |
| 무결성 요구 | 트랜잭션·유니크 제약·소유권 검증 필요 | 읽기 전용 — 쓰기 충돌 자체가 없음 |
| 주 소비자 | Java (Spring/JPA) | **Python** (AI 추천 파이프라인) |

**바뀌는 데이터는 DB가, 바뀌지 않는 데이터는 파일이 정답**이라는 일반 원칙에 정확히 부합한다. 카탈로그를 DB에 넣으면 "읽기 전용 정적 데이터"에 트랜잭션·커넥션·스키마 관리 비용을 지불하는 셈이고, 유저 데이터를 파일에 넣으면 동시 쓰기·무결성이 깨진다.

---

## 3. 카탈로그를 파일로 둔 이유 4가지

### ① 소비자가 Python이다 — DB를 주면 오히려 결합이 생긴다

카탈로그를 읽는 코드는 전부 **Python AI 파이프라인**이다(`loader.py`가 단일 소스로 로드, `lru_cache`로 1회만 파싱). 만약 카탈로그가 DB에 있었다면:

- Python에 **DB 드라이버·접속 정보·스키마 의존성**이 추가된다 (현재 Python은 표준 `json` 모듈 하나로 끝).
- Spring DB 스키마가 바뀌면 Python도 같이 깨진다 — **두 런타임이 스키마로 결합**된다.
- 현재 구조에서는 Spring↔Python 접점이 **stdin/stdout JSON 계약 하나**뿐이라, 서로의 내부를 몰라도 된다.

> 실제 계약: Spring이 진단 결과·수강이력을 JSON으로 `bridge.py`에 넘기고, Python은 카탈로그 파일로 과목명→코드 매핑·후보 필터·성향 분석을 수행한다. **사실 판정(학점·GPA)은 이미 Spring이 끝낸 값을 그대로 쓴다**(원칙 1: 판정은 규칙 기반 Java).

### ② 카탈로그는 "빌드 산출물"이다 — 데이터라기보다 코드에 가깝다

```
data/raw/courses_eval.csv    (과목별 평가 특성 — 팀이 조사·태깅)
data/raw/courses_areas.json  (과목별 이수구분·영역)
        │
        ▼  build_data.py  (교과목코드로 병합, 미태깅은 null)
data/courses.json            (병합본 — 런타임이 읽는 단일 소스)
```

- 원천 2개를 **빌드 스크립트로 병합**해 만드는 산출물이다. 갱신 절차가 "SQL UPDATE"가 아니라 **"원천 수정 → 재빌드 → 배포(scp)"**로, 코드 배포와 같은 리듬이다.
- **git으로 버전 관리**된다 — 언제 어떤 과목 특성이 바뀌었는지 diff로 추적 가능. DB에 넣으면 이 이력이 사라진다.
- 실제 운영에서도 이 흐름을 썼다: 전공 특성 11과목 보강 → 재빌드 → EC2 업로드 (7/15).

### ③ 규모가 파일에 맞다 — DB의 이점이 발동할 크기가 아니다

- 182건 · **약 108KB**. 통째로 메모리에 올려 `lru_cache`로 쓰는 게 인덱스·쿼리보다 단순하고 빠르다.
- DB가 이기는 지점(대용량 검색, 부분 조회, 동시 쓰기, 페이징)이 **하나도 필요 없다.**

### ④ 데모 재현성 — 발표 리스크 최소화

- 카탈로그가 파일이면 AI 파이프라인은 **DB가 죽어도, 스키마가 바뀌어도** 영향받지 않는다.
- 배포도 단순하다: `scp`로 파일 하나 올리면 끝. 마이그레이션·시딩 스크립트가 없다.

## 4. 유저 데이터를 DB에 둔 이유 (대칭 논거)

- **동시 쓰기·무결성**: 회원가입 이메일 유니크, 프로필 1:1 제약, 소유권 검증(`403 PROFILE-003`)은 DB 제약과 트랜잭션이 필요하다.
- **사용자별 상태**: 계정마다 다른 데이터를 조회·수정하는 패턴은 JPA/SQL이 정확히 맞는 자리다.
- **영속성**: H2 파일 모드(`jdbc:h2:file:...;AUTO_SERVER=TRUE`)로 재시작·재배포에도 유지 — EC2에서 검증됨.

## 5. 대안 비교 — 왜 다른 안을 안 골랐나

| 대안 | 기각 이유 |
|---|---|
| **카탈로그도 DB에** (Course 카탈로그 테이블 신설) | Python에 DB 의존성 추가, 스키마 결합 발생, 갱신 이력(git) 상실, 엔티티·마이그레이션·시딩 작업 추가 — **얻는 기능 0** |
| **카탈로그를 Spring API로 노출** (Python이 HTTP 조회) | 호출마다 네트워크 왕복, Spring 다운 시 AI도 다운, 엔드포인트·DTO 추가 — 파일 1회 로드보다 모든 면에서 복잡 |
| **유저 데이터도 파일로** | 동시 쓰기 충돌, 유니크 제약 불가, 트랜잭션 없음 — 명백히 부적합 |
| **양쪽 다 DB + Python도 DB 접속** | 두 런타임이 한 스키마에 결합, MVP 기간 대비 과설계 |

## 6. 정직한 트레이드오프 (한계와 대응)

| 한계 | 내용 | 대응 |
|---|---|---|
| **이름 정확일치 매핑** | Spring DB 수강이력엔 과목코드가 없어, Python이 카탈로그 이름 색인으로 매핑(공백 트림 후 exact match). 카탈로그에 없는 과목명은 성향분석에서만 빠짐 | 학점 계산엔 영향 없음(그건 Spring 진단이 끝낸 값). 에러가 아니라 성능 저하로만 격리됨 |
| **캐시 비재생성** | 추천 캐시의 지문(fingerprint)은 유저 데이터만 반영 — **카탈로그를 고쳐도 캐시가 자동 재생성되지 않음** | 카탈로그 갱신 시 수동 재생성 절차로 운영(문서화됨) |
| **이중 소스 인지 비용** | "과목"이 두 곳(유저 수강이력=DB, 카탈로그=파일)에 있어 혼동 여지 | 역할이 다름을 문서로 명시: DB=학생이 들은 것, 파일=학교가 개설한 것 |
| 운영 확장 시 | 다학과·수천 과목 규모가 되면 카탈로그도 DB(또는 검색엔진)가 맞음 | MVP 이후 과제로 명시 — 현재 1학과 182건에는 파일이 최적 |

## 7. 예상 반론과 대응 (방어 Q&A)

> 심사·질의에서 나올 법한 "왜 굳이 그렇게? 그게 최선인가?" 공격과, 그에 대한 대응. **인정할 트레이드오프는 인정하고, 대신 그 약점이 어디로도 못 새게 격리했음을 보인다.**

### Q1. "과목 카탈로그도 그냥 DB 테이블로 만들면 되잖아요. 그게 정석 아닌가요?"
🛡️ 정석은 "무조건 DB"가 아니라 **"데이터 성격에 맞는 저장소를 고르는 것"**입니다. 이 카탈로그는 **읽기 전용·정적·소비자 하나(Python)**입니다. DB가 이기는 지점(트랜잭션·동시 쓰기·부분 조회·유니크 제약)이 **하나도 필요 없고**, DB로 옮기면 Python에 드라이버·접속·스키마 의존성이 새로 생겨 Spring 스키마와 결합됩니다. 이득 0, 결합 비용만 증가 — 그래서 이 데이터엔 파일이 정석입니다.

### Q2. "과목명 문자열로 매칭한다고요? 이름이 조금만 달라도 실패할 텐데, 취약한 설계 아닌가요?" *(가장 날카로운 지점)*
⚖️ **맞습니다. 이름 정확일치 매핑은 취약합니다.** 인정합니다. 다만 그 취약성이 **어디로도 못 새게 격리**했습니다.
🛡️ ① 매칭에 실패한 과목은 **성향 분석(AI 보조 층)에서만 빠지고**, 학점·GPA·졸업 판정(규칙 층)에는 영향이 **0**입니다 — 그 판정은 Spring 진단이 이미 끝낸 값을 그대로 쓰기 때문입니다. 즉 **이름 매칭이 틀려도 잘못된 졸업 판정이 나오는 일은 구조적으로 불가능**합니다. 최악의 경우는 "추천이 조금 덜 개인화됨"뿐입니다.
🛡️ ② 사용자는 성적표의 과목'명'을 입력하지 과목'코드'를 모릅니다. 코드 입력을 강요하는 게 오히려 나쁜 UX입니다.
🔭 향후: 운영 확장 시 입력 단계에서 카탈로그 자동완성으로 코드를 확정 → 이름 매칭 자체를 제거.

### Q3. "데이터가 두 곳에 나뉘면 정합성(consistency)이 깨지지 않나요?"
🛡️ 두 데이터는 **겹치는 가변 상태가 없습니다.** DB=학생이 들은 과목(트랜잭션 데이터), 파일=학교 개설 과목(참조 데이터). 서로 동기화해야 할 공유 값이 없어 정합성 문제 자체가 성립하지 않습니다. 연결은 요청 시점의 **무상태(stateless) 이름 조회** 하나뿐입니다.
⚖️ 단 하나의 정합성 포인트 — 카탈로그를 고치면 추천 캐시가 자동 재생성되지 않음 → **수동 재생성 절차로 운영**(문서화됨).

### Q4. "파일이면 동시 접근·락 문제는 없나요?"
🛡️ 런타임에는 **쓰기가 0**입니다. `lru_cache`로 프로세스당 1회 로드 후 메모리에서만 읽습니다. 쓰기가 없으니 **락·경합이 구조적으로 발생 불가**합니다(쓰기는 빌드 타임·오프라인·단독으로만). 이 데이터에 한해선 파일이 DB보다 오히려 안전합니다.

### Q5. "AI를 굳이 Python 별도 프로세스로? 두 언어·두 런타임은 과설계 아닌가요?"
🛡️ AI 실패(타임아웃·Gemini 장애)를 **JVM 본체와 격리**하려는 의도입니다 — Python이 죽어도 Java 서비스는 안 죽습니다(타임아웃 + 캐시 폴백). 또 "판정은 규칙(Java), AI는 보조(Python)" 원칙이 **프로세스 경계로 물리적으로 강제**됩니다.
⚖️ 두 런타임은 이동 부품이 느는 비용이 있어, 접점을 **stdin/stdout JSON 계약 하나**로 최소화했습니다.

### Q6. "182건이라 파일이 낫다는 건, 확장 못 하는 설계라는 인정 아닌가요?"
🛡️ "확장 못 함"이 아니라 **"필요 없는 확장을 미리 짓지 않음(YAGNI)"**입니다. 읽는 지점이 `loader.py` **한 곳**뿐이라, 규모가 커지면 그 한 함수만 DB/검색엔진 조회로 바꾸면 됩니다 — 이관 비용이 **국소적·예측 가능**합니다. 실제 규모(1학과·182건)에 최적화한 판단이며, 확장 경로도 이미 확보돼 있습니다.

### Q7. "데이터를 git(코드 저장소)에 넣은 게 데이터/코드 분리 위반 아닌가요?"
🛡️ 이 카탈로그는 **유저·운영 데이터가 아니라 파생 참조 설정**(원천에서 빌드한 산출물)입니다 — 시드 데이터·i18n·설정 파일을 코드와 함께 버전 관리하는 것과 같은 범주(**config-as-code**)입니다. 유저·운영 데이터는 전부 DB에 있습니다(git엔 없음). 오히려 소규모 큐레이션 데이터라 **diff로 변경 이력을 추적**하는 이점이 큽니다.

### Q8. "저장소로 MySQL을 아예 안 썼네요? 유저 데이터는 H2, 카탈로그는 파일 — 왜 둘 다 MySQL이 아닌가요?"
🛡️ **몰라서가 아니라, 자원 제약에 맞춘 의도적 선택**입니다. 두 부분으로 답합니다.
- **유저 데이터(H2)**: 서버가 **프리티어 EC2 한 대(2GiB)**이고, 이 한 대에서 JVM 앱과 **AI용 Python 프로세스**가 함께 돕니다. 독립 MySQL을 올리면 상주 프로세스가 하나 더 얹혀 **커밋 메모리가 약 3배(실측 ~336MB→~1GB)**로 늘어, 동시 부하 시 AI 처리에 쓸 여유를 잠식합니다. H2도 **SQL·JDBC·JPA를 그대로 쓰는 정식 RDB**라 코드 경로가 MySQL과 동일하고, **파일 모드로 영속성**도 확보했습니다. 실제로 **MySQL 전환을 검증**했고 JPA 표준이라 **설정 프로파일만 바꾸면** 동작함을 확인했습니다.
- **카탈로그(파일)**: 여긴 MySQL이 **더더욱** 안 맞습니다(Q1). 읽기 전용 정적 182건을 위해 DB 서버를 띄우는 건 순수 오버헤드입니다.
⚖️ 실제 대규모 운영이라면 넉넉한 사양 + 독립 MySQL/RDS가 맞습니다 — 그건 운영 단계 과제로, **전환 경로까지 검증해 뒀습니다.**
> 상세 실측·부하 근거: `docs/MySQL_전환작업_리포트.md` §7 (AI 서브프로세스 75MB/개, H2 vs MySQL 커밋 비교).

### 한 줄 방어 원칙
> **"바뀌는 데이터는 DB, 안 바뀌는 참조 데이터는 파일. 약한 고리(이름 매칭)는 AI 보조 층에만 두어 규칙 기반 판정은 절대 오염되지 않게 격리했다."**

## 8. 발표 멘트 (요약)

> "데이터를 성격에 따라 둘로 나눴습니다. **회원·수강이력처럼 계속 바뀌는 데이터는 DB**에 두고 트랜잭션과 소유권 검증을 걸었고, **개설과목 카탈로그처럼 바뀌지 않는 읽기 전용 데이터는 파일**로 두고 git으로 버전 관리했습니다.
> 카탈로그의 유일한 소비자가 AI 추천을 담당하는 Python 파이프라인이라, 파일로 두면 Python이 DB에 의존하지 않아 **두 런타임이 JSON 계약 하나로만 연결**됩니다. 182건짜리 정적 데이터에 DB를 쓰면 복잡도만 늘고 얻는 게 없다고 판단했습니다.
> 물론 다학과·수천 과목 규모로 확장하면 카탈로그도 DB로 옮기는 게 맞고, 그건 운영 단계 과제로 남겨뒀습니다."

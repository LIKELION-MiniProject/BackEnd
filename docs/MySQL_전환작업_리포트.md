## 4. 기존 백엔드 코드·연동을 손상시켰나? → **아니오**

세 겹으로 안전하다.

### 4-1. `main` 브랜치·배포본 무영향
- 모든 변경은 `feat/mysql` 브랜치에만 있다. `main`은 **동결된 상태 그대로.**
- 로컬 커밋만 했고 **원격(EC2)에 push하지 않았다.** 배포 서버는 이 작업을 알지도 못한다.

### 4-2. H2 동작 무영향
- H2 접속 설정(`application.yml`)·H2 시드(`data.sql`)를 **수정하지 않았다.**
- H2 데이터 파일(`data/passportdb.mv.db`)은 `.gitignore` 대상이라 git이 건드릴 수 없고, 이번 작업 내내 **한 번도 열리지 않았다.** (데이터는 전부 MySQL 쪽 `passportdb`에만 기록)
- `mysql` 프로파일을 주지 않으면 앱은 여전히 **기본값인 H2로 부팅**한다. 추가된 MySQL 커넥터는 프로파일을 선택했을 때만 쓰인다.

### 4-3. API 계약·FE 연동 무영향
- 엔드포인트·DTO·응답 형식·인증 방식 등 **API 계약을 전혀 바꾸지 않았다.**
- FE가 호출하는 대상은 EC2 배포 서버(`http://15.164.84.176/api/v1`, H2 기반)이고 그건 그대로다.
- 따라서 **FE 연동 가이드(문서 100번)는 수정 없이 그대로 유효**하다.

> **요약** : 변경은 전부 격리된 브랜치의 *추가분*이며, 배포본·H2·API 계약 어느 것도 바뀌지 않았다.

## 5. 발표용 — Workbench에서 데이터 보여주는 절차

목적: "우리 앱 데이터가 실제로 MySQL에 저장된다"를 화면으로 증명.

### 준비 (앱을 MySQL로 한 번 실행해 데이터 채우기)
1. PowerShell(프로젝트 폴더)에서 §2-3 명령으로 앱 실행.
2. 앱이 뜨면 로그인→프로필→수강 추가를 한 번 수행 (FE로 하거나, 아래 검증 스크립트로).
   - 이미 로컬 검증 때 넣은 데이터(`TestCourse` 등)가 남아 있으면 이 단계는 생략 가능 (MySQL은 영속이라 앱을 꺼도 데이터가 남는다).

### 스크린샷 1 — 스키마·테이블 트리 *("MySQL에 우리 DB가 있다")*
1. Workbench 홈에서 **`PassPort`** 연결 더블클릭.
2. 왼쪽 **SCHEMAS** 패널에서 `passportdb` → **Tables** 펼치기.
3. `courses`·`profiles`·`users`·`certifications` 등 테이블 목록이 보이는 화면을 캡처.

### 스크린샷 2 — 실제 데이터 *("데이터가 MySQL에 저장됐다")*
1. 상단 툴바에서 새 쿼리 탭 열기.
2. 아래 붙여넣고 **⚡(Ctrl+Shift+Enter)** 실행:
   ```sql
   USE passportdb;
   SELECT id, name, credit, category, grade FROM courses;
   SELECT id, user_id, dept_code, name FROM profiles;
   SELECT id, email, nickname FROM users;
   ```
3. 아래 **Result Grid**에 행이 채워진 화면을 캡처. (한글 닉네임이 정상으로 보이는 것도 포인트)

### (선택) 스크린샷 3 — 라이브 반영 *("실시간으로 MySQL에 쌓인다")*
1. 앱을 켠 상태에서 FE(또는 API)로 수강 과목 하나 추가.
2. Workbench에서 위 `SELECT * FROM courses;`를 **다시 실행**(⚡).
3. 방금 추가한 행이 새로 나타나는 걸 캡처 → 앱↔MySQL 연동을 실시간으로 증명.

> **팁** : Result Grid 상단 **Export** 버튼으로 결과를 CSV로 저장해 자료로 첨부할 수도 있다.

## 7. H2 선택 명분 — 부하 측정 근거 (실측)

### 7-1. 왜 H2인가 (우선순위 순)

1. **단일 인스턴스 아키텍처** — EC2 **t3.small(2GiB, 프리티어) 한 대**에 JVM 앱 + AI용 Python 서브프로세스 + nginx가 함께 올라간다. 여기에 독립 DB 서버까지 두면 설치·기동·백업·보안 등 **운영 부담**이 늘고 **상주 메모리**를 상시 점유한다. H2 내장은 그 부담이 0.
2. **동시 부하 여유 확보(실측 근거 아래)** — 한 대에서 JVM과 Python이 동시에 뜨는 구조라, MySQL 상주분(수백 MB)을 아껴 **동시 AI 처리 여유**로 돌렸다.
3. **MVP 속도·데모 재현성** — 내장 DB라 앱과 함께 배포·재현. 파일 모드로 영속성도 확보.

> ⚠️ 사실관계: **t3.small은 이 계정에서 프리티어로 확인됨**(콘솔 배지). 프리티어 micro(1GiB)가 아니라 **더 여유 있는 2GiB(프리티어)를 선택**했다. "프리티어라 메모리가 부족했다"가 아니라 "프리티어 범위에서 여유 사양을 골랐다"가 정확하다.

### 7-2. 부하 측정 (로컬 실측 → 2GiB 대입)

| 구성요소 | 실측 | 측정 방법 |
|---|---|---|
| JVM 앱 (유휴) | 상주 **287 MB** | 포트 8080 java 프로세스 WorkingSet |
| **AI Python 서브프로세스** | **75 MB / 개** (~9초, Gemini 라이브) | `bridge.py` 실제 스폰, 피크 상주 샘플링 |
| AI 동시 3개 | **225 MB** (75×3, 선형 증가) | 3개 동시 스폰, python 상주 합계 피크 |
| mysqld (독립 프로세스) | 상주 ~74 MB(유휴·트림) / 커밋 **~716 MB** | 로컬 실행 중 프로세스 |

> ⚠️ MySQL 상주(RSS)는 Windows가 유휴 시 트림해 낮게 나온다. **커밋(committed)이 더 안정적인 비교 지표**다. 설정은 버퍼풀 128MB + `performance_schema` ON(자동 사이징)이며, 리눅스 기본 RSS는 대략 수백 MB이고 튜닝 시 더 낮출 수 있어 **"정확히 400MB"로 단정하지 않는다.**

#### H2 vs MySQL — 상주·커밋 직접 비교 (실측)

H2는 **JVM 안에서** 동작해 별도 프로세스가 없다. MySQL은 JVM 위에 얹히는 독립 프로세스다.

| 구성 | 프로세스 | 상주 합계 | 커밋 합계 |
|---|---|---|---|
| **JVM + H2 (현재)** | 1개 | ~287 MB | **~336 MB** |
| **JVM + MySQL** | 2개 | ~360 MB | **~1,050 MB** |

→ H2는 추가 프로세스·추가 예약이 거의 0(JVM 힙 내부, DB 파일 86KB). MySQL로 바꾸면 **커밋 메모리가 약 3배(336MB→~1GB)**로 뛴다. "MySQL이 400MB"라는 하드 넘버 대신 **이 구조적 비교(커밋 약 3배)**가 정확하고 반박이 어렵다.

**2GiB(t3.small) 예산 대입:**

| 항목 | 메모리 |
|---|---|
| OS + nginx | ~250 MB |
| JVM 앱 (`-Xmx1g`, 부하 시) | ~1,200 MB |
| 고정 소계 | ~1,450 MB |
| 남는 여유 | ~600 MB |

| 시나리오 | 동시 AI 수용량 (÷75MB/개) |
|---|---|
| **H2 (현재)** | 여유 ~600MB → **~8개** — 동시 5명도 여유 |
| **+ 독립 MySQL** (리눅스 상주 보수적 ~300MB 가정) | 여유 ~300MB → **~4개** — 동시 처리 여유가 **절반 이하로 감소** |

**결론:** 동시 사용 시 메모리 압박의 **주 원인은 DB 커넥션이 아니라 요청마다 뜨는 AI Python 서브프로세스(각 75MB)**다. H2는 JVM 내부라 별도 상주 프로세스가 없어(커밋 ~336MB) 그 여유를 **동시 AI 처리량**으로 쓸 수 있다. MySQL을 상주시키면 **커밋이 ~3배(→~1GB)**로 늘어 동시 처리 여유가 절반 이하로 줄어든다. (숫자를 단정하기보다 "커밋 약 3배"라는 구조적 사실로 말하는 게 안전하다.)

**측정 한계(정직한 단서):** ① 프로세스 발자국은 로컬 Windows 실측이라 EC2 Linux RSS와 다소 차이 가능(자릿수 수준 근거). ② 캐싱 설계상 GET은 캐시로 응답(Python 미스폰), **데이터가 바뀐 POST만** 스폰하므로 "동시 5명 동시 스폰"은 평상시가 아닌 **최악 시나리오**. ③ 최대 소비자는 상한 고정된 `-Xmx1g` JVM.

### 7-3. 발표 멘트 (부하 근거 포함)

> "서버는 프리티어 t3.small(2GiB) 한 대이고, JVM 앱과 **요청마다 뜨는 AI용 Python 프로세스**가 함께 돌아갑니다. 측정해보니 AI 프로세스는 하나당 약 75MB를 쓰고, 사용자가 몰려 동시에 실행되면 그만큼 선형으로 쌓입니다. H2는 JVM 안에서 동작해 별도 프로세스가 없지만, MySQL로 바꾸면 독립 프로세스가 얹혀 실측상 **커밋 메모리가 약 3배(약 1GB)**로 늘어 동시 처리 여유가 절반 이하로 줄어듭니다. 그래서 DB는 내장 H2로 자원을 아껴 **동시 부하 여유를 확보**했고, 파일 모드로 영속성도 유지했습니다. JPA 표준이라 실제 MySQL 전환도 설정 수준으로 검증해 두었습니다."
